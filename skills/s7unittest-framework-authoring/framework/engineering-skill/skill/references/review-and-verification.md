# Review Changes And Verify Engineering Claims

Use the applicable [rule sources](rule-sources.md) and inspect the actual artifact. A successful generator, complete file read, matching argument name or passing pattern check is evidence only for what it actually checks.

## Review The Source Independently Of Its Construction

Reconcile the requested behavior and preserved before-state with declarations and code. Trace the relevant paths and actual symbols, not a summary saying the rule was applied. Focus the review on correctness and change risk; do not require a fixed report schema or another general analyzer.

- Re-derive consequential operand, intermediate and destination/formal types, units and ranges, including external symbol/constant definitions. Check arithmetic/comparisons, guards, counts/indices, assignments and call bindings against those actual declarations, the block IEC setting and applicable instruction semantics. Check operand alignment in the actual expression, not just whether the current numbers fit. An unresolved declaration is an unresolved type review; a plausible literal, correct API binding or safe final datatype does not rescue it or an unsafe intermediate.
- Apply the general guide's [conversion matrix and context boundaries](s7-styleguide.md#directed-conversion-matrix), using the IEC-on conversion rules even for blocks with IEC check disabled. Reject reliance on IEC-off-only implicit transitions in newly authored or changed conversions; require warning-free diagnostics in the actual target mode as well. Check necessary explicit transitions and avoidable conversion boilerplate together: preserve IEC-conforming warning-free implicit conversions, question inconsistent local type choices and repeated casts, and reject meaningless aliases or extra state/work introduced merely to reduce cast counts. Do not infer a cast requirement from differing type names, another operator/context or documentary availability alone. Neither IEC acceptance, a warning-free result nor an explicit cast establishes range/precision safety. Do not change existing block settings as a review shortcut.
- Verify constants, initial values, types, bounds and numeric representations together with executable behavior. Confirm required distinctions and acceptance relationships; do not replace them with observed DUT output or accept changed values because the displayed text rounds identically.
- Check declarations by the applicable object/section/datatype/storage context against the authoritative matrices and project refinement. Include supported attribute representation, inherited/defining members, relevant containers and preservation of unrelated settings. Source tokens alone do not establish effective native properties.
- Trace initialization/reset/restart, invalid configuration/state, active/inactive, success/failure and cleanup paths as relevant to the block. Review defaults before reads, actual call/sample order, state/command ownership, timers/edge memories, output assignments and previous-cycle memorization. Preserve a domain framework's required ordering and semantics.
- Reconcile interface/dependency impacts, namespace/symbol resolution, identities/header metadata and readable source structure with the approved change. Apply the general guide's Software Unit/library-copy context table to actual destination placement; distinguish public API eligibility from publication and relations, and do not impose unit access barriers outside units. Check that implementation constants resolve to suitable accessible definitions or intentional local declarations, while shared/contract definitions retain their authority. Do not count an accidental duplicate symbol as the intended update or a logic/attribute rewrite as formatting-only work.

For the applicable paths, trace the guide's concrete execution constraints rather than checking keywords: loop termination through the final control update and zero-iteration paths; explicit guards before dependent operations; separated mutable expression calls; rounding for negative values/ties and the actual result type; shared actual storage and copy-back effects; and the selected timer's ownership, invocation, observation and reset model. Do not assume short-circuit evaluation or passive timer-output reads. Keep deterministic-output/temporary-before-read rules intact without adding redundant defaults. When ENO is error evidence, verify its actual generation/settings and when the value is captured and rearmed; neither the existence of an ENO read nor blanket resets establish correct error attribution. Use the general guide's existing sections, not a second technical matrix.

Apply the general guide's responsibility/interface, cyclic-code, refactoring, test-only-boundary and observability rules to the design as well as its syntax. Check the actual code for these concrete review questions:

- Can the block's purpose, inputs/results, mutable state owner and externally visible side effects be understood from its name, declarations and local processing? Trace hidden DB access, forwarding layers and shared writes rather than accepting a small parameter list as proof of low coupling.
- Do compound expressions describe one coherent signal meaning, or compress unrelated properties so that their intent is obscured? Check whether a meaningfully named intermediate expression makes the information clear; splitting a formula into meaningless aliases does not improve it.
- Does each stored flag, phase/state copy, helper layer or generic mechanism have a distinct current responsibility? Trace reads/writes and the domain framework's existing behavior before accepting extra bookkeeping. Identify redundant control paths without replacing framework-defined ordering or introducing another state controller.
- Do initialization, failure, reset and cleanup leave a defined observable state? Can the relevant behavior be driven and observed through intentional interfaces and dependencies without test-only production branches or externally writable internal state? Review practical testability; do not add test scenarios, hooks or new public interfaces without approval.
- Would a proposed extraction or reuse layer clarify a coherent responsibility, or merely fragment the cyclic path and add calls, copying, storage or diagnostic indirection? Examine consequential loop bounds, data volumes and call multiplicity for the required use. Report an unknown material resource/timing constraint; do not invent a budget, mandate benchmarking or introduce a new decomposition policy.

Compilation, static checks and passing behavior tests do not establish these design properties. Report a material finding and its concrete consequence under the existing rules, not a personal preference as a new requirement. A missing normative design rule or an architecture change requires owner alignment; this review does not authorize a redesign.

For a requested review, report consequential findings with precise artifact locations and consequences before a brief summary. Distinguish confirmed defects from unresolved facts and preferences. When no findings are identified, state the review boundary and remaining evidence gaps; do not imply compiler or runtime coverage that was unavailable.

## Apply And Read Back Only Within Authorized Scope

Use the project workflow for target verification, before-state protection, writes, failure handling and fallback approval. Use available concurrency guards. Before a native verification action, identify the intended target/artifacts, the observable completion condition and a finite observation limit. Configure finite connection/read timeouts where the API supports them and bound polling of asynchronous results. A polling deadline cannot interrupt a blocked synchronous native call; identify that limitation rather than promising cancellation or introducing a process-killing watchdog.

Submit an approved state-changing request once, then observe it within the bound rather than resending a possibly accepted request. On timeout, disconnect or an incomplete response, retain what was submitted, the last observation and what remains unknown. Inspect actual state before any coordinated retry or dependent mutation; do not silently switch engineering paths, assume rollback or replay a partially applied batch. Do not restart, reset, download, delete or close the owner's project/session as automatic recovery. Release handles/connections and close temporary hosts only where they were created and are owned by the operation and the workflow permits that cleanup; cleanup is not another PLC command.

Compare the stored result with the intended artifact semantically, including declaration values and bounds, identities, required attributes and executable behavior. Account for known serializer normalization only where meaning is actually preserved. A comparison that removes all attributes or whitespace may support a limited claim, but cannot independently prove effective properties, text values or readable indentation.

For an import, whole-object replacement, rename or move, compare the intended before/after object and dependency inventories with the live result and saved artifact. Verify the unique target identity, expected namespace/location, fields/sections/bodies and references; check affected adjacent members where the format can alter their boundaries. Missing or duplicate objects, lost dependencies or a body attached to the wrong declaration are structural defects even if the import was accepted. Do not derive apparent source repairs solely from the input file when the stored structure differs.

After a native rename or move, re-read current declarations and usages before further replacements: the engineering environment may already have rewritten references. Require the expected target/matches for the next edit; an unchanged section is not evidence of a successful replacement. Use native identities and actual relationships, not an assumed folder order or an unverified text range. If creation or a structural check fails, stop dependent edits until the actual target and required dependencies are established. These checks do not authorize editing TIA-owned source exports or choosing another import path.

For precision-critical data, verify the relevant stored value distinctions rather than trusting rounded diagnostics or unchanged executable tokens. Obtain default-inclusive/native-property evidence when omitted attributes prevent verification, and follow storage/type relationships to their actual definitions. Matching representative qualification can establish a supported representation; verify the required properties of the affected artifacts, not just the representative.

Do not rewrite a correct value/property merely to force explicit export tokens. When the available readback cannot establish a required fact, state that exact gap and use an agreed evidence path before claiming the affected scope verified. This is not permission to invent another startup/release flag or ask the owner to make the technical implementation choice.

## Assess Diagnostics And Behavior Separately

Compile the relevant approved scope under its existing workflow and review the diagnostics, not only tool success. Distinguish newly introduced, pre-existing and unresolved warnings, retaining their location/message until corrected or explicitly accepted. Do not silence diagnostics through unsupported casts, changed accepted inputs, omitted required checks or unrelated source edits.

When import or compilation fails, trace the first relevant causal diagnostic against the actual stored object and dependencies before treating cascading errors as independent defects. Separate a source-language/type problem from a serialization/structure problem, missing or wrong project dependencies, target-state mismatch or tool limitation. The first displayed row is not necessarily the cause. For example, a missing-type report after a failed type import or move requires inspecting that type and its binding before rewriting every caller. Retain the full diagnostic evidence, correct only the established cause within scope, then reassess the remaining findings; do not discard independent errors or claim a cause from message ordering alone.

An incremental check that compiled nothing is not an actual complete rebuild. Follow the project's meaningful compilation gates without rebuilding every block individually or extending scope to other PLCs. Where the tool cannot perform a required rebuild/readback, report its capability limit and agree the permitted operation; an owner-operated tool step does not transfer code correctness to the owner.

Choose behavioral verification from the actual changed behavior and risk. Metadata/import qualification does not require artificial PLC runtime tests. Source correctness or a successful compilation does not prove startup, timed behavior, cleanup or reuse; obtain applicable runtime evidence before making those claims. Do not expand a source-only task or add scenarios without authority.

## Close With Evidence, Not Another Policy

Summarize the implemented change or concrete findings, the source/native/property/compilation/runtime evidence actually obtained, and material unresolved limits. Separate prerequisites, request submission/acceptance, observed storage/completion and any behavioral result. A tool success flag or cleared request does not establish the intended final state or a passing domain result. If current observations cannot be distinguished from an earlier completed operation, report that ambiguity rather than success. Keep reports proportional and use the project's evidence location; do not deposit per-run reports in permanent skill documentation.

When generation or review exposes an error, evaluate whether it is an isolated editing/application mistake, a missing or ambiguous instruction/example, an unsupported syntax/representation assumption or a recurring tool limitation. Read the responsible existing guidance and related rules together before proposing a correction. An instruction already present but not applied does not automatically justify adding another rule; record the missed application and recheck the affected work. Fixing generated code alone does not establish that a reusable guidance gap was resolved.

For a justified guidance correction, identify the responsible source: general coding policy, project refinement/workflow, Engineering method, domain skill or qualified representation. State the correct action, its trigger, supporting manufacturer reference or scoped native observation, relevant target/version/context limits and exceptions. Keep independent skills independent and do not turn an unverified workaround into a universal restriction. Apply only corrections authorized by the task; align changes to normative policy, agreed responsibilities, behavior or scope before applying them. If no guidance change is warranted, state why in the work evidence.

When an approved correction adapts or consolidates existing guidance, compare the final text with the complete relevant source passages, not only a summary or isolated search hits. Preserve concrete triggers, required actions, evidence, limits and exceptions. Record necessary platform adaptations and justified exclusions in the work evidence. Resolve conflicts with related rules before removing superseded wording; do not replace an operational instruction with a weaker generic intention or append a competing policy merely to satisfy the latest example.

Do not promote release-only full-project quality/inventory gates into every edit/build/commit. This engineering pass does not authorize policy changes, publication, version increments, PLC downloads/control or the next work package. Preserve the consuming project's normal handoff and acceptance responsibilities.
